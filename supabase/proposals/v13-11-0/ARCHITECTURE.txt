Goleszan 19 v13-11-0 — архитектура и безопасность
Основа: cc79574b2d5fd80851d323e5e2134fea570d71e7, Draft PR №8.
Реализация подготовлена локально. Миграции и развёртывание НЕ выполнялись.

Согласованные решения

Серверное разграничение без E2EE. Веб-администратор не имеет дополнительных
прав на чужие диалоги. Владелец БД/инфраструктуры технически может читать
открытый текст — это честно указано в раскрываемом пояснении интерфейса.
Архив доступен оставшемуся участнику, пока действует его собственный период.
Новый жилец никогда не наследует прежнюю историю по одному номеру комнаты.
Архив не принимает новые сообщения и ответы; цитаты и пагинация читаются.

Что установлено в исходной реализации

Жители используют отдельные случайные device tokens: сервер проверяет SHA-256,
revoked_at и rooms.generation. Supabase Auth применяется отдельно для веб-админа.
Общий чат — g19_private.messages, страницы по 40, polling 5–30 секунд,
реакции по комнате/generation. Таблицы закрыты RLS и отсутствием API grants.

После последнего Odłącz существующий release_empty_room меняет occupied, но
НЕ generation. Следующий жилец мог бы получить тот же ключ (room,generation).
Поэтому личная история использует независимый private period UUID.

Существующая категория messages, числовые event_key и массовое прочтение
означали только общий чат. Их нельзя было напрямую расширить личными событиями:
старые bigint-преобразования и auto-read клиента затрагивали бы чужой контекст.

1. Периоды, идентичность и архив

Миграция 020 создаёт private_periods/private_current_period. Текущие устройства
комнаты разделяют период. Последний Odłącz или административный Zwolnij pokój
завершает его; отключение одного из двух устройств период не меняет.
Авторизация, токены, лимит устройств и auth generation не переопределяются.

Диалог уникален по канонической паре (room_low,period_low,room_high,period_high).
Смена любого участника закрывает старый диалог для отправки. Оставшийся участник
видит его в Archiwum и читает через прежний UUID, пока его собственный период
действует. Подключённое им дополнительное устройство разделяет этот доступ.
После завершения обоих исходных периодов доступ из приложения отсутствует;
записи сохраняются в БД, автоматического удаления/восстановления нет.

Новая пара текущих периодов получает новый пустой диалог. Пока комната свободна,
она видна в списке, но отправка невозможна. Пустые сообщения или диалоги ради
списка не создаются: запись диалога появляется транзакционно с первым сообщением.

Сервер отдельно проверяет чтение (свой исходный действующий период) и отправку
(оба исходных периода действуют). Нет доверия к client-side readOnly или p_room.
Период адресата фиксируется при открытии и передаётся в send; смена жильца во
время ввода/повтора запроса не перенаправляет черновик новому человеку.

Невозможно определить смену человека, пока старое устройство остаётся
авторизованным. При фактической передаче комнаты нужен Zwolnij pokój.
Подтверждение дополнительного устройства означает доступ к текущей истории;
это поясняется в инструкции подключения.

Для новых общих сообщений сохраняется sender_period. Ссылка автора в личную
переписку разрешена только при подтверждённой актуальности автора. Старые
сообщения без такого снимка допускают ссылку лишь для ещё действующего устройства
того же поколения; сомнительный старый автор не превращается в нового жильца.
Собственная комната и прежние жильцы не предлагаются как личные собеседники.

2. Схема и API

020_private_chat_foundation:
• периоды и их ротация при освобождении комнаты;
• private_conversations и private_members — пара комнат и участников;
• private_messages — UUID, локальный seq, автор, request_id, тело, reply_to;
• private_read_cursors — общий комнатный курсор конкретного диалога/периода;
• private_presence — присутствие устройства/вкладки в конкретном диалоге;
• nullable reply_to/sender_period общего чата и приватный контекст inbox;
• private_chat_settings, по умолчанию enabled=false.
Новые таблицы имеют RLS без разрешающих политик и без прямых прав API-ролей.
Проектный SQL перемещён из proposals в supabase/migrations после согласования.

021_private_chat_api:
• capabilities, список текущих диалогов, архив с пагинацией;
• отправка, чтение, переход к оригиналу, scoped activity/read cursors;
• общий send_reply/read с сохранением старых трёхпараметрных send/read API;
• notifications_v2 и совместимость старых клиентов;
• нейтральные приватные события и service-only проверка перед доставкой.
Вспомогательные функции не доступны API. Публичные личные операции требуют
device token. Административный JWT не заменяет личность комнаты.

Составной FK (conversation_id,reply_to) запрещает чужую приватную цитату.
Курсор также ссылается на сообщение того же диалога. В ответах хранятся только
ссылки, без копии полного оригинала. Сервер возвращает краткую цитату.
Чужой и неизвестный UUID диалога дают одинаковый отказ. Поле запроса не позволяет
назначить автором другую комнату. UPDATE/DELETE личных сообщений не предоставлены.

Чтение/оригинал/активность используют проверку своего периода. Отправка и
BEFORE INSERT guard дополнительно запрещают запись в архив. Идемпотентность
проверяет устройство, request_id, адресата/период, тело и ссылку ответа.
Применяется существующее ограничение отправки 2 секунды, общее двум видам чата.

3. Конкурентные транзакции

Блокировки комнат берутся по возрастанию номера перед блокировкой устройства.
Отдельная revision/последовательность принадлежит диалогу; личные сообщения не
меняют chat_revision общего чата и не выдают чужую активность через общий ID.

На PostgreSQL 16.15 воспроизведён deadlock: два отправителя удерживают устройства
FOR UPDATE, один ждёт диалог, другой при создании уведомления ждёт FK KEY SHARE
на устройство получателя. В 021 изменён только режим блокировки устройства
на FOR NO KEY UPDATE. Он продолжает сериализовать отзыв и rate-state, но
совместим с FK-проверками неизменяемых идентификаторов устройств.
Проверки токена, generation, revoked_at и порядок блокировки комнаты сохранены.
Курсоры при массовом прочтении обрабатываются в порядке UUID диалогов.

Отдельный scripts/test_private_concurrency.py проверяет на частном /tmp Unix-
сокете: воспроизведение старого deadlock, обе встречные отправки после фикса,
одновременное read-all двух устройств и гонку send с освобождением комнаты.
Тест создаёт только свою БД, после проверки удаляет её. Реальный Supabase и
сетевой push не используются. Временный сервер после проверки остановлен.

4. Уведомления и счётчики

Настройка messages остаётся общей настройкой push сообщений устройства:
охватывает Ogólne и Prywatne. Новых категорий и подписок не создаётся.
Получатели приватного события — только активные устройства другой комнаты
нужного периода, без уведомления собственной комнаты отправителя.
Ключ события private:<message UUID>; тело переписки отсутствует в inbox metadata,
ответе push_take для личного события, payload и журналах доставки.
Push нейтрален: «Nowa wiadomość prywatna od pokoju nr N».

Имеющаяся очередь, lease, retry/backoff, лимиты попыток, VAPID, allowlist endpoint
и Cron сохранены. Обновляется лишь классификация приватного payload и проверка
актуальности перед отправкой. После закрытия диалога незавершённая приватная
доставка недопустима. Уже принятый внешней push-службой запрос невозможно
гарантированно отозвать — поэтому содержимого личного сообщения в нём нет.

Текущий общий счётчик 019 сохранён. Личные непрочитанные считаются по серверным
курсорам исходного периода и синхронизируются устройствам комнаты. Prywatne
включает доступные текущие и архивные диалоги; Archiwum показывает свой остаток.
Шапка Dyskusje суммирует общий и личный счётчики, не прибавляя inbox повторно.
Просмотр Ogólne не прочитывает личные сообщения; просмотр одного личного диалога
не прочитывает остальные. Явное «отметить все» v2 обновляет и личные курсоры.

Legacy notification_read/activity и notifications отделены от приватных событий.
Все bigint-преобразования messages защищены CASE. Присутствие в общем чате не
подавляет push другого личного диалога. Личное прочтение подтверждается только
для загруженного конца истории видимой, сфокусированной и недавно активной
страницы. Курсор монотонен, поздний ответ не возвращает его назад.

5. Интерфейс, навигация и хранение на устройстве

Ogólne по умолчанию; Prywatne показывает три другие комнаты, превью/дату/счётчик.
Archiwum появляется только при наличии закрытых диалогов. Это простой список
и экран чтения без формы отправки/ответа, без поиска, экспорта или удаления.
Доступные цитаты и старые страницы продолжают открываться.

Команды Odpowiedz есть в общем и активном личном чате. Над вводом — автор,
краткая цитата, отмена. Переход к оригиналу загружает окно истории при
необходимости и выделяет строку. Неизвестный/недоступный оригинал даёт пояснение.
Реакции общего чата сохранены; новые реакции личного чата не добавляются.

Маршруты: #dyskusje, #dyskusje/prywatne, /pokoj/N для ещё не начатого диалога,
/archiwum и /<UUID>. Push ведёт только к строгому UUID-адресу в своём scope.
История браузера и обычные ссылки сохраняются. Собственный заголовок календаря
скрыт существующим sr-only, id=calendar-title и семантическое имя сохранены.

Черновики разных диалогов/периодов хранятся отдельно только в памяти страницы.
Приватные тела не сохраняются в localStorage, shell-кэше SW или постоянной
клиентской БД. Обновление страницы может потерять неотправленный черновик.
При отзыве устройства/смене token очищаются память и DOM. Поздние ответы другого
контекста игнорируются; запросы активности упорядочены. Периодический опрос
проверяет архивный статус, не срывая чтение старых страниц.

6. Проверки и практические пределы

Итог: 29/29 основных Node.js тестов; 19/19 Python тестов. После усиления
проверок повторно пройдены 10/10 сценариев объявлений/PWA и личного чата,
включая потерянный ответ отправки без дубликата и отдельные черновики.
Нативный PostgreSQL 16.15 подтвердил все пять результатов из пункта 3.

Автоматические проверки используют PGlite и настоящий локальный HTTP/Chromium:
обычные сообщения/ответы/оригиналы вне окна, реакции общего чата, два устройства,
отдельные черновики, счётчики, архив в обеих темах на 390/1280 px, отказ новому
жильцу, подмена UUID/цитаты/курсора, admin JWT без обхода, прямой CRUD/RLS,
точные адресаты и нейтральный push, legacy read-state, отключённый feature flag,
атомарный отказ при ALL TABLES publication, PWA/scope/существующие регрессии.
Отдельно выполнены реальные многосессионные PostgreSQL-пробы из пункта 3.

Это не live-проверка конфигурации Supabase Auth/Realtime или системной доставки
Android/Linux: они требуют отдельного разрешения на тестовое внедрение.
Исходники не используют Realtime, приватные таблицы не публикуются. Миграция
останавливается при публикации FOR ALL TABLES; перед применением нужны read-only
preflight и проверка actual grants/publications в явно выбранном тестовом проекте.
Блокировка новых серверных чтений не может отозвать уже доставленный человеку
открытый текст; модель не обещает абсолютной конфиденциальности или E2EE.
