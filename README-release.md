# Goleszan 19 · публикация тестового Cloudflare Pages

Workflow рассчитан на `Axylion/sprzatanie-mieszkania`, проект `goleszan-19-preview` и его текущий адрес `https://goleszan-19-preview.pages.dev/`. Секрет `CLOUDFLARE_API_TOKEN` и переменная `CLOUDFLARE_ACCOUNT_ID` берутся из настроек репозитория. Идентификатор аккаунта сверяется с известным значением. Cloudflare Pages project, custom domains и Supabase не изменяются.

## Этапы и записи

| Тег | Что выполняется | Что хранится |
|---|---|---|
| `g19-release-<версия>-api` | GET проекта и текущего Production. Проверяет окружение, домены, конфигурацию и успешный статус точки отката. | `g19-stage/record.json` с полным ID Production, URL, веткой и хешем конфигурации. |
| `g19-release-<версия>-preview` | Собирает проверенный source SHA на отдельном раннере без секрета Cloudflare. Проверяет тестовый Supabase, PWA и Service Worker. Публикует в Preview после получения сохранённого ZIP. Проверяет, что исходный Production остался активным. | `g19-candidate` содержит `dist.zip` и `build.json` с SHA-256 ZIP, путями, числом и SHA-256 файлов. `g19-stage` содержит полный Preview ID и URL. |
| `g19-release-<версия>-functional` | Подтверждение владельца после ручного чек-листа. Автоматика сверяет содержимое всех опубликованных файлов Preview с ZIP. | `g19-stage` связывает отметки с Preview ID, source SHA, SHA-256 ZIP и прогонами GitHub. |
| `g19-release-<версия>-production` | Повторно проверяет API, точку отката, успешный Preview, Functional Check и хеши. Разворачивает содержимое того же ZIP через Wrangler. Сверяет активный Deployment и опубликованные файлы на привычном адресе. | `g19-stage` содержит предыдущий и новый полные ID, одобренный Preview и автоматические проверки. |
| `g19-release-<версия>-post` | Подтверждение владельца после проверки устройства и настроек. Повторно сверяет сайт, опубликованные файлы и доступность исходного Deployment. | Итоговый `g19-stage` с отметками устройства, Service Worker и уведомлений. |

Все теги одного релиза указывают **на один и тот же коммит управления релизом**. Коммит управления содержит workflow, скрипты и манифест. Поле `source_sha` указывает отдельно на точный коммит приложения. После первой отправки тегов используйте новый идентификатор релиза для любого изменения манифеста или workflow. Workflow сверяет репозиторий, имя и ID инициатора, создание тега, попытку запуска, коммит управления и происхождение артефактов по результатам GitHub Actions. Для публикации используются только артефакты нужных запусков на этом коммите. Подмена ZIP проверяется SHA-256, подмена файлов — хешами из записи Preview.

Теги заменяют `workflow_dispatch`, который требует наличия workflow в default branch. Не переиспользуйте имена тегов и не удаляйте их. На стороне GitHub используйте по возможности ruleset для `g19-release-*`, чтобы ограничить создание тегов владельцем и запретить их обновление и удаление. Коммиты контроля релизов должны быть доступны для просмотра до подтверждения. Пользователь с правом менять workflows и запускать их в репозитории в общем случае может злоупотребить доступным repository secret. Для команды с недоверенными авторами перенесите токен в ограниченные GitHub Environments с правилами доступа и отдельными проверками. Такой переход требует изменения настроек и в данном пакете не выполняется.

## Подключение на Linux Mint

Выполните этот блок только после согласования первого **API Check**. Предполагается, что ZIP скачан в `~/Downloads`, незакоммиченных файлов нет, а существующий локальный репозиторий содержит коммит UI8. Если файл скачан в другое место, измените `archive`. После установки файлов в хранилище репозитория блок создаёт новый локальный коммит и отправляет только API-тег.

```bash
(
  set -euo pipefail
  cd "$HOME/goleszan-ui8-deploy"
  repo=Axylion/sprzatanie-mieszkania
  remote="https://github.com/$repo.git"
  archive="$HOME/Downloads/goleszan-pages-release.zip"
  base=2fa2360df431048ecf807c1e05ed7045c03bafc7
  test "$(gh api user --jq .login)" = Axylion
  test -z "$(git status --porcelain)"
  if ! git cat-file -e "$base^{commit}" 2>/dev/null; then
    git fetch "$remote" "$base"
  fi
  git switch -c release/goleszan-pages-v2 "$base"
  unzip -n "$archive"
  python3 -B scripts/g19-release/test_release.py
  git add -- .github/workflows/goleszan-pages-release.yml \
    scripts/g19-release/{release.py,test_release.py,package.json,package-lock.json} \
    releases/{example.json,ui8-audit.json} README-release.md
  git diff --cached --check
  git diff --cached --name-status
  git commit -m "Add staged releases for Goleszan test Pages"
  gh auth setup-git
  git push "$remote" HEAD:refs/tags/g19-release-ui8-audit-api
)
```

Посмотрите результат командой `gh run list -R Axylion/sprzatanie-mieszkania --branch g19-release-ui8-audit-api --event push`. Если GitHub CLI не разрешает добавить новый workflow, проверьте область `workflow` у вашей локальной авторизации GitHub. Если GitHub Actions отключены, проверьте настройки репозитория. Эти проверки не требуют значения токена Cloudflare.

## Следующий релиз

1. Подготовьте source SHA приложения в этом же репозитории, локально запустите тесты приложения и проверьте сборку. Скопируйте `releases/example.json` в `releases/<version>.json`. Идентификатор версии содержит от 1 до 30 символов, строчные латинские буквы, цифры и дефисы. Укажите ожидаемую версию Service Worker и точный SHA. `expected_file_count: null` означает «посчитать фактическое количество». Заполните число, если оно известно после предыдущей локальной сборки. Записанные в артефакт хеши обязательны в обоих случаях.
2. Проверьте diff манифеста и создайте коммит управления в отдельной ветке. Один коммит управления можно сохранить для аудита на отдельной ветке, если хотите. Его SHA должен оставаться тем же для всех тегов одного релиза. Присвоив `commit` и `version`, отправьте один тег:

```bash
git push https://github.com/Axylion/sprzatanie-mieszkania.git \
  "$commit:refs/tags/g19-release-${version}-api"
```

3. После успеха API Check и отдельного разрешения на Preview повторите команду с суффиксом `-preview`. Получите URL и полный ID из summary.
4. На этом Preview проверьте интерфейс, календарь и дежурства, список средств и инструкции, объявления и обсуждения, настройки и навигацию, светлую и тёмную темы, мобильное отображение, PWA и Service Worker, консоль на критические ошибки JavaScript. Проверки выполняются без удаления или повторной регистрации устройств, изменений пользовательских данных и отправки push. Пуш тега с суффиксом `-functional` под аккаунтом Axylion означает, что **каждый пункт прошёл**. При сбое сохраните наблюдения вне workflow, тег не отправляйте. Используйте новый релиз для исправленной версии. Автоматическая сверка опубликованных файлов выполняется после этого тега.
5. После успешного Functional Check и отдельного разрешения на Production повторите команду с суффиксом `-production`. Сразу сверяйте новый полный ID и автоматическую проверку основного тестового адреса. Проверьте активную версию Service Worker через инструменты браузера и проверьте ранее подключённое устройство и его настройки уведомлений без очистки данных. После успешной проверки можно зафиксировать результат тегом `-post`.
6. Скачайте аудиторские записи и кандидат до истечения хранения. Для конкретного запуска используйте `gh run download RUN_ID -R Axylion/sprzatanie-mieszkania -n g19-stage -D audit/RUN_ID`. Для Preview дополнительно скачайте `g19-candidate` в другой каталог. Сохраняйте эти файлы вместе с коммитом управления в вашем резервном хранилище. GitHub Actions запрашивает хранение 90 дней, политика организации может устанавливать меньший срок. При истечении артефакта процесс останавливается и для публикации потребуется новый ID релиза с прохождением всех этапов.

## Возврат к предыдущему Production

1. Найдите `baseline.production_id` в записи API Check или Production. Сверьте проект `goleszan-19-preview`, основной адрес и текущий активный Deployment.
2. В Cloudflare Dashboard откройте **Workers & Pages → goleszan-19-preview → Deployments**. Успешный Production Deployment с этим полным ID должен быть доступен. До отдельного разрешения не нажимайте подтверждение отката. После разрешения выберите **Rollback to this deployment** и подтвердите.
3. Проверьте, что прошлый ID вновь активен и сайт обслуживается на том же адресе. Проверьте Service Worker и устройство без очистки браузера. Запишите время, оба ID и результат. Если Deployment удалён или недоступен, остановитесь и согласуйте восстановление из проверенной резервной копии по обычному релизному процессу. Автоматического отката здесь нет.

## Ограничения и проверка

- Сериализация GitHub относится к этому репозиторию и группе workflow. GitHub может отменить прежний ожидающий запуск при поступлении нового. Отправляйте следующий тег после окончания предыдущего. Внешняя публикация вне Actions этим не блокируется. Между последним GET и командой Wrangler остаётся короткое окно гонки. При неожиданном результате остановитесь и сверьте историю Cloudflare.
- После неясного ответа Wrangler, сетевого сбоя или ошибки smoke-проверки публикация могла состояться. В таком случае сначала проверьте Cloudflare по записи попытки и активному ID. Не повторяйте запуск вслепую.
- Проверка секретов в файлах эвристическая. Кандидаты должны содержать только публичную статическую конфигурацию. Поддерживаются статические сборки без Cloudflare Functions, серверных конфигурационных файлов и неожиданных привязок доменов. Хеш опубликованных файлов проверяется без браузера. Ручная проверка отвечает за поведение клиента и сохранение регистрации.
- Схема GitHub tags проверена на данных прошлого запуска UI8. Новый workflow проверялся локально. Первый запуск в реальном GitHub Actions должен выполнять только API Check.
