# Goleszan 19 — одна постоянная тестовая площадка

## Единственный адрес для просмотра и проверки

**https://goleszan-19-preview.pages.dev/**

Каждая новая версия публикуется непосредственно на этот адрес. После публикации пользователь проверяет интерфейс и поведение сайта здесь; исправления выходят сюда же. Предварительный Preview, отдельные ветки публикации Cloudflare, промежуточные сайты и альтернативные адреса в рабочем процессе не используются.

Проект Cloudflare Pages: \`goleszan-19-preview\`. Это Direct Upload-проект. Workflow проверяет, что Git-интеграция и Pages Functions не появились неожиданно, и разворачивает файлы только в фактическую Production-ветку проекта (сейчас \`main\`). Публикация в любую другую ветку запрещена.

## Текущий переход: F1 UI10-r3

- Source SHA: \`4eab4b02533bae427df15c80198791117ee547df\`
- Service Worker: \`goleszan19-shell-v13-11-0-f1-ui10-r3\`
- Ожидается 68 статических файлов.
- Кандидат, ранее собранный для UI10-r3, имеет SHA-256 ZIP \`c6b4d50680a52304a243cc95de4ede82936fb322839b6e3890de216ccb932f90\`. Повторная сборка должна дать тот же хеш, иначе публикация останавливается до обращения к Cloudflare.

## Единый цикл релиза

1. Подготовить точный коммит приложения и обновить \`releases/<version>.json\` в управляющей ветке \`release/goleszan-permanent-test\`.
2. Выполнить локальные тесты приложения и проверить source SHA, Service Worker и конфигурацию тестового Supabase.
3. Создать коммит управляющей ветки с точным сообщением \`release: publish <version>\`. Только такой коммит от владельца запускает релиз.
4. GitHub Actions выполняет офлайн-регрессию релизного механизма, собирает статический ZIP с точного source SHA, проверяет файлы, PWA, Service Worker, конфигурацию Supabase и секреты.
5. Перед публикацией workflow считывает текущий Production Deployment, проверяет его успешность и сохраняет полный ID как точку отката.
6. Тот же проверенный ZIP разворачивается через Wrangler только в Production-ветку Cloudflare Pages. Workflow не создаёт Preview Deployment и не использует URL отдельных deployment.
7. Автоматика проверяет активный Production ID и побайтно сверяет все опубликованные файлы именно на постоянном адресе выше. Также проверяется доступность предыдущего Production Deployment для ручного отката.
8. После успешного прогона пользователь проверяет сайт по постоянному адресу. Следующая версия выпускается после его замечаний и подготовки следующего source SHA.

Отдельная предварительная ручная приёмка Preview отсутствует. Успешная публикация означает, что сборка и автоматические проверки прошли; ручная проверка интерфейса и реального устройства остаётся за пользователем.

## Что сохраняется

- \`main\` и PR #8 не меняются и не объединяются.
- Supabase, пользовательские записи, устройства и настройки уведомлений не изменяются.
- Для каждого релиза сохраняются ZIP с хешами файлов и запись GitHub Actions с исходным и новым полными Deployment ID.
- Предыдущий Production Deployment остаётся доступен как внутренняя точка ручного отката. Откат не выполняется автоматически.
- Cloudflare deployment history остаётся служебной историей. Её внутренние ID и автоматически выдаваемые адреса не используются как площадки для просмотра или тестирования и не выводятся в пользовательскую инструкцию.

## Очистка старых Preview

При первом прямом релизе workflow попытается удалить существующие Preview Deployments проекта. Cloudflare может запретить удаление последнего deployment конкретной ветки; такие записи будут перечислены в итоговом аудите, без попыток менять Production. Cloudflare документирует, что Preview URL остаётся доступным до удаления deployment, а последний deployment ветки удалить нельзя: https://developers.cloudflare.com/pages/configuration/preview-deployments/.

Будущие релизы не создают Preview Deployments: workflow всегда использует Production-ветку проекта и проверяет только постоянный URL. Поскольку проект Direct Upload, автоматические Git Preview-сборки не используются.

## GitHub Actions

Workflow: \`.github/workflows/goleszan-pages-release.yml\`.

Требуемые настройки репозитория остаются прежними:
- Secret: \`CLOUDFLARE_API_TOKEN\`
- Variable: \`CLOUDFLARE_ACCOUNT_ID\`

Токен передаётся только в job публикации. Сборка и тесты не получают Cloudflare credentials. Wrangler и GitHub CLI не получают секрет Cloudflare одновременно.
